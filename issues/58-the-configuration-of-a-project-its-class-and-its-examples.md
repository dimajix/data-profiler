# 58 — The configuration of a project: its class and its examples

**Status:** open
**Type:** refactoring
**Priority:** low
**Area:** Command line
**Summary:** `Project` takes each field of its configuration as a constructor parameter of its own only to keep it, and the example project, the README and PROJECT.md show the configuration otherwise than it is - without the semantic types, the separator of lists or the contract, and of an older format.

## The problem

The reviews of [57](57-export-as-open-data-contract.md) found what is not clean around the
configuration of a project, which that work did not change on its own, as AGENTS.md asks:

1.  **`Project` takes its configuration apart.** `Project.read` is the only caller of
    `Project.__init__` (`src/data_profiler/project.py`, around line 215). It takes the
    `_Configuration` it read apart field by field - `types`, `list_separator`, `llm`, `contract`,
    `environments` - and `__init__` stores each unchanged in an attribute of its own; only `tables`
    is changed on the way, compiled into a `Pattern`. Every field added to the configuration costs
    a constructor parameter, an argument in `read` and an assignment: 57 added the fourth such
    field, `contract`. That is a parameter passed on only to be passed on, which AGENTS.md counts
    against a design.
2.  **The example project does not show each field.** PROJECT.md says of `examples/crm/` that "its
    files show each field of the configuration" (around line 497), but `project.yml` there gives
    no `types`, no semantic type of the project.
3.  **The directory table of PROJECT.md misses a field.** Its row of `project.yml` (line 16) names
    the tables, the semantic types, the language model, the contract and the environments, but not
    the separator of lists, `list_separator`.
4.  **The README shows an outdated example.** The snippet the README presents as `examples/crm/`
    (around line 121) is of `format: "4.0"`, without `list_separator` and `contract`, and the list
    below it names neither. The tool still reads it, as an older minor version, but it is no longer
    the example it says it is.
5.  **One condition of the sentinels is written twice.** "The sentinels of a column are those given,
    else those of the tool, and none where the database writes its values as no text" is written in
    `src/data_profiler/statistics.py` (lines 54-56) and in `Contract._missing` of
    `src/data_profiler/contract.py`, each as `has_text` and then `detect.sentinels`.

## Why it matters

The first makes every new field of the configuration more expensive than it needs to be, and hides
that `Project` adds nothing to most of what it holds. The next three are documents a developer reads
before writing a project: an example that lacks a field, or is of another format than the tool
writes, teaches the configuration wrongly, and the claim that the example shows each field makes a
reader stop looking. The last is small, but it is the kind of repetition that drifts apart when one
of its places changes.

## Considerations

**1, `Project`.** `Project` holds the `_Configuration` it read, beside the compiled `tables`, its
file and its variables; `types`, `list_separator`, `llm`, `contract` and the environments are read
from it. `__init__` takes the configuration rather than its fields. The public attributes `tables`,
`types` and `list_separator` and the properties stay what they are to the callers, so that only
`project.py` changes. To check: whether `_Configuration`, private, may then be the type of a
parameter of a public constructor - `Project.read` stays the only way a project is made, so that
`__init__` may become private to the module in effect, as it is today.

**2, the example.** Either the example project gets a semantic type of its own - one the simulation
generates values of, so that the example still profiles the simulation environment as it does -,
or the sentence is narrowed to the fields the example shows. A type of the project in the example
is the better choice if the simulation has a column it fits; otherwise the narrower sentence.

**3 and 4, the documents.** The row of PROJECT.md names `list_separator`. The README either shows
`examples/crm/project.yml` whole - PROJECT.md already embeds it, generated by
`scripts/generate.py` between markers, which the README could take over so that it cannot drift -,
or it shows a shorter snippet that does not claim to be the example. The generated copy is
preferred, as it is checked.

**5, the sentinels.** A function of one place would take whether the type has text, which the
coding guidelines warn of as a boolean that switches a function between two behaviours; the
condition is one line in each place. The proposal of the work on 57 was to leave it as it is. To
decide: leave it, or find a form without that boolean - such as a method of the dialect, which owns
`has_text`, giving the sentinels of a column of a type.

## Done when

`Project` holds its configuration rather than its fields, with no change to its callers; PROJECT.md
and the README describe the configuration as it is - the example project showing each field or the
sentence saying which it shows, the directory table naming every field, the README's example the
current one -; and the condition of the sentinels is in one place, or the decision to leave it is
recorded here.
